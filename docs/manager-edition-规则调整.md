## Sam 的 4 条决定

1. 交付延期维持每周 −4。
2. 审计要计入评分。零审计打法（2 个实质动作 + 3 次 oem_please_act）分数要低于好策略，同时不能重开 B1/F1。
3. 安全分 ≤25 判变砖，按含所有扣分的最终安全分判定，结局文案要一致。
4. 同一个实质动作重复做只算 1 次。这一条后来改成配置开关，开和关两种数据都要给 Sam 看。

## 方案

### 规则 2：知情度加分

`insightBonus = (无高风险项 || 高风险修复周数 ≥ knowing_waive_min_repair_weeks) && 实质改善数 ≥ min_improve_actions ? 审计方向数 × audit_bonus_per_dir : 0`

加分放进加权和的 Math.round 里面，总分上限 100。

为什么要带前提条件：
- 如果不带条件直接给审计加分，B1 打法（3 个方向都审计、然后全部放行）会拿回分数。
- 现在加分和「知情后真的去修」绑在一起。B1 打法的加分为 0，结果仍是 B·74（代号 10）。
- F1（noop 过半封顶）的逻辑没有改动。

加分系数调参，看 300 个代号上零审计打法与好策略的比较：

| 每方向加分 | 零审计高于/持平好策略 | 好策略 A（simulate 3000） |
|---|---|---|
| 1 | 2 / 36 | 1007 |
| **1.5（采用）** | **0 / 0** | 1010 |
| 2 | 0 / 0 | 1734（偏松） |

### 规则 3

- 高风险放行扣分从变砖判定之后移到之前，`isBrick = 最终安全 ≤ 25`。
- 如果变砖时没有严重事故（rain_ped/ghost/brake），副标题使用 `PENALTY_BRICK_SUBTITLE`：「多项高风险红线带病放行，安全评审一票否决，项目上路前被叫停」。安全原因里会写出放行项数。
- SOP 提示改为：「安全分 ≤25 直接判定项目失败」。

### 规则 4

`improveCount` 在开关打开时取不重复的动作 id 数，关闭时取原始次数。它只影响「实质改善 <2 封顶 B」和规则 2 的前提条件。
